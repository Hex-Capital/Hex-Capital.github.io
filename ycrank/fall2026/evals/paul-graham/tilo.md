# Tilo -- Paul Graham Evaluation

On October 21, Tilo’s catalogue authorization expired and devices lost access. This is the most useful founder test in the dossier. Something broke. The documented response includes renewal procedures, monitoring metrics, and clearer expiry messages. But it does not establish who repaired it, how quickly, or whether the repair restored access and prevented recurrence. I cannot turn an incident report into evidence of resourcefulness. I would want the short, concrete account of what the founders did next.

The product gives me a stronger reason to pay attention. Tilo exposes typed application actions while keeping human and agent activity inside shared state, permissions, history, and undo. There is public implementation code and an application SDK behind that description. This fits a pattern I like: giving programmers a primitive from which they can build things the founders haven’t imagined. It earns substantial technical credit. The claimed improvement of up to 10,000 times cheaper computer use does not earn additional credit without a reproducible comparison. A working implementation and an extraordinary performance claim require different standards of proof.

The difficult question is why the first developer will adopt it. Browser Use structures existing websites; Tilo asks applications to describe their resources and actions to obtain its deeper capabilities. That additional work could produce a much better environment. It also puts integration work between the developer and the benefit. The strongest bull case is that shared permissions, collaboration, and undo solve problems that a collection of automation tools cannot solve cleanly. But the dossier identifies no developer repeatedly accepting that integration burden. Three stars on a GitHub mirror do not establish rejection, especially when the main repository lives elsewhere. They also cannot substitute for someone needing the product.

Wolff’s patent-workflow automation at BDPE during 2025–2026 makes the founders more interesting than two people who merely noticed that agents were fashionable. Their shared TUM and BDPE affiliations provide relevant context. They do not establish that Tilo arose from a particular workflow they personally could not complete, or that the pair has already worked through a difficult disagreement. Nor is there a documented rejected hypothesis followed by a changed product. I would leave those questions open rather than infer either exceptional adaptability or stubbornness. The unfinished security boundaries make the concrete first workflow especially important: its requirements will tell them which difficult work matters now.

I would pass today. Tilo fits my preference for programmable infrastructure, but the dossier has not demonstrated either the founder response to resistance or the narrow well of urgent users that would make me write a personal check. There is no established dependence on a large partner or evidence of premature delegation; this is not a pass based on those red flags. I also considered whether the working-product exception should override the missing founder evidence. The implementation is promising, but neither unmistakable user pull nor independently validated technical performance supplies that override. One verifiable result would make me reconsider: a documented founder-led integration cycle that turns a named customer’s blocked workflow into a deployed Tilo application, followed by that customer using it weekly for a month.
