# GitCafe -- Cyan Banister Evaluation

Six years from now, coding agents may generate most routine commits, while humans govern intent, provenance, and deployment risk. In that world the repository is less a browser destination than a machine-readable coordination layer. GitCafe has one plausible leak from that future: an npm-installed CLI that handles authentication, pull requests, credentials, and agent-skill installation. But the dossier never completes the causal chain. It does not show which agent behavior breaks today’s git infrastructure, why a custom engine fixes it, or how teams move from GitHub’s 630 million repositories to this new operating model without several unnamed miracles.

The technical artifact is real. GitCafe built libgitz, the kiln runtime, a native `cafe:git` binding, a forge, stacked diffs, and a first-party CLI rather than decorating the standard git binary. That is the most compelling part of the company because it matches my concealed-infrastructure pattern: build beneath the visible AI wave and control something downstream products may need. The problem is that technical depth is not yet a scarce bottleneck. GitHub, GitLab, Bitbucket, and open-source forges can reproduce workflow features, while GitCafe still plans the migration and CI compatibility required to displace them. Owning the stack matters only if the stack enables behavior the incumbents structurally cannot support.

Veronica has credible building evidence: 72 public repositories, Rust and TypeScript work, platform bindings, and prior experience as a founding engineer at Corgi. Shipping this much of a forge with a two-person team is stronger than a résumé assembled around a fashionable category. Still, I cannot see the dated pre-company obsession, independently derived git experiments, complementary recruiting story, or commercial command that would establish the full Rizz–Tizz–Biz pattern. The dossier also does not clarify the co-founder relationship or decision control. There is no documented 50/50 governance problem or leadership shell game, but accountability would be a diligence gate before my money moved.

Eight named organizations are presented as users, which proves that the beta is more than a rendering. It does not yet prove costly or weird behavior. There are no cohorts, migration counts, repeat-use figures, payments, or examples of engineers entrusting GitCafe with their primary private repositories. Free private repos and beta terms permitting discontinuation make experimentation cheap precisely where the product needs to demonstrate trust. Source-code custody also raises my privacy gate: the legal, privacy, and abuse channels are responsible surface signals, but the dossier supplies no limiting architecture, consent model, or security proof sufficient for sensitive organizational code.

The missing system economics keep me from an invest decision. GitCafe calls itself a GitHub replacement, but it does not identify a specific fee, restriction, queue, or institutional rule that GitHub imposes; nor does it quantify the rent being removed or the agency returned to developers. The strongest bull case is that the eight organizations discovered an agent-native workflow before the category had language for it, and the custom engine is therefore infrastructure rather than feature theater. My pre-revenue exception can cover missing revenue when a functioning artifact, unusually deep founder history, and institutional commitments converge. Here only the artifact is well established.

My base case is that within 36 months GitCafe either pivots from a general GitHub replacement into an agent-native git engine and workflow API or remains below $2 million ARR as a respected niche forge. One fact would flip me: three named organizations moving their primary private repositories to GitCafe, paying for them, and showing weekly repeated use of an agent workflow that GitHub cannot reproduce without changing its architecture. That would turn the eight-logo curiosity into the mundane artifact leaking from a much larger future.
