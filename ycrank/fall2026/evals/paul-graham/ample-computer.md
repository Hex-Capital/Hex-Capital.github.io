# Ample Computer -- Paul Graham Evaluation

Ample Computer has shipped something. What I cannot find is the episode that would tell me most about its founders: a deployment broke, a user needed it fixed, and they found a way through. Ravi’s Shopify experience and reported earlier acquisition are relevant background. They do not establish how this team behaves when blocked. I give the product credit separately; inferring resourcefulness from its existence would count the same evidence twice.

The strongest evidence is the infrastructure itself. Ample exposes deployment through an MCP connector and CLI, runs code in isolated microVMs, and returns a URL and diagnostic logs. Anthropic lists its connector, and Ishan published a [production implementation report dated October 17, 2026](https://github.com/personal-agent-protocol/personal-agent-protocol/issues/15). This is substantially beyond a diagram. The evidence supports a functioning product, though the company-authored report supplies no independently measured reliability or performance threshold. Ample fits my pattern of backing programmable interfaces for new users—in this case, agents—but has yet to show the numerical proof spike that makes an unfamiliar infrastructure bet easier to underwrite.

The interesting question is whether letting an agent deploy first and a human claim the application afterward changes who can build software. If it removes the moment when an otherwise successful coding session dies inside cloud configuration, that could matter a great deal. Railway and Render already offer agent integrations, so the decisive evidence would be users choosing Ample repeatedly because this particular workflow saves them. The [six showcased applications](https://ample.computer/) do not establish that: ownership, payment, and repeat usage are undisclosed. Per-second billing with a one-minute minimum describes how Ample could collect money, rather than showing anyone wants to keep paying.

The strongest case against passing is that two people have already assembled a usable deployment system and put it where agents can discover it. A small group of developers could make that system indispensable before the larger providers notice the particular need. That possibility deserves attention. But the working-prototype exceptions in my framework require unusually revealing founder behavior or unmistakable validation alongside the artifact. Neither appears here. The Claude connector is a distribution surface; I would not call it evidence of a dangerous partnership dependency. Likewise, an undocumented cofounder history does not establish a hastily assembled team. Those red flags are unproven.

I would pass on the present evidence. There is no documented evidence-driven route change, so adaptability receives the missing-evidence default. There is also no account connecting the founders’ own deployment difficulties to Ample’s origin; related employment alone cannot supply it. My condition for reopening the investment decision is one verifiable customer episode: a named user encounters a deployment blocker, the founders ship a workaround within a week, and that user subsequently deploys through Ample weekly for a month. That would connect the technical artifact to both founder behavior and a real need. Today, the artifact is carrying almost the entire argument.
